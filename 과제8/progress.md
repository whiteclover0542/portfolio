### 자동 검증 결과 요약 (2026-09-07, 로컬 `evidence/log.md` + 배포 `evidence-prod/log.md` 둘 다 동일하게 통과)
- 로그인 전: `#private-content`는 화면에 없고, HTML 소스에도 비공개 텍스트 없음. `/api/private` 무쿠키 요청 → **401**.
- 등록: `/api/register-options`를 같은 아이디로 두 번 호출 → challenge 값 서로 다름 확인. 등록 성공 시 서버 응답에 공개키 미리보기만 포함(개인키 없음). 위조된 attestation으로 검증 시도 → 400, 이후 해당 계정에 저장된 credential 0개 확인.
- 로그인: 로그인 성공 시 세션 쿠키 발급 → `/api/session` `loggedIn:true`. 방금 성공한 로그인 요청 바디를 그대로 재전송 → **401 "이미 사용됨"** (challenge 1회용 확인). 로그아웃한 옛 세션 쿠키 재사용 시도 → **401**.
- 기기 분실: alice 계정에 패스키 2개(`alice-노트북`, `alice-폰`) 등록 → 목록에 이름+등록일 표시 → `alice-노트북` 삭제 → 남은 `alice-폰`으로 재로그인 **성공** → 삭제된 credential id로 로그인 시도 시 **401 "이 계정에 등록된 패스키가 아닙니다."**
- 교차 계정: alice·bob 두 계정 각각 패스키 등록(메모 내용도 서로 다름 확인) → alice의 credential id로 bob 계정에 로그인 시도 **401**, 반대 방향도 **401** (양방향 확인) → alice 세션으로 로그인한 채 쿼리스트링·헤더에 `bob-demo`를 지정해도 응답은 항상 alice 자신의 메모만 반환.
- 배포 주소(whiteclover-portfolio.vercel.app)에서도 위 전체 시나리오가 동일하게 통과 (rpID가 실제 도메인으로 정확히 잡힘, Redis에 실제로 저장/조회됨).

## 작업 순서 (카드 순서대로)

1. **카드 1** — index.html에 비공개 섹션 UI 자리 추가(항목 3개+), 공개/비공개 경계를 화면에서 명확히. 서버(또는 API)에서 비공개 데이터는 로그인 없이 요청 시 401/403으로 거절되게 만들고, 로그아웃 상태로 받은 HTML/응답 본문에 비공개 내용이 없는지 직접 확인.
2. **카드 2** — WebAuthn 등록 플로우 구현: 서버가 challenge 생성·보관 → 브라우저 `navigator.credentials.create()` → 공개키 서버 저장 → 패스키 이름 붙이기. 취소 시 아무것도 저장되지 않는지 확인.
3. **카드 3** — WebAuthn 로그인 플로우 구현: 서버가 매번 새 challenge → `navigator.credentials.get()` → 공개키로 서명 검증 → 세션/토큰 발급. challenge 재사용 거절, 로그아웃 후 거절 확인.
4. **카드 4** — 같은 계정에 패스키 2개 등록 → 목록 화면(이름·등록일) → 하나 삭제 → 남은 것으로 로그인 성공, 삭제한 것으로는 실패 확인.
5. **카드 5** — 계정 2개 만들어 교차 접근 시도(양방향) 기록, 로그인 없이 비공개 주소 직접 열기 기록, 인증 구현 설명서 6항목 작성, 짧은 확인 방법 4줄·AI 3줄 작성.

> 공개 주소를 바로 열어 3단계 이내 행동으로 30초 안에 끝낼 수 있게 작성.

### 어디로 가나요
- https://whiteclover-portfolio.vercel.app

### 세 단계 안에 무엇을 하나요
1. 위 주소를 연다 — WHO AM I~PROJECTS까지는 그대로 보인다 (1번 과제와 동일).
2. 아래로 스크롤해 PRIVATE 구역에서 아이디를 아무거나 입력하고 "패스키 등록"을 누른다 (내 기기의 생체인증/PIN 창이 뜬다).
3. 등록이 끝나면 비공개 메모·등록된 패스키 목록이 바로 열린다. "로그아웃" 후 같은 아이디로 "패스키로 로그인"을 눌러도 다시 열리는지 확인한다.

### 무엇이 보이면 통과인가요
- 로그인 전에는 PRIVATE 구역에 비공개 메모가 전혀 보이지 않는다(등록/로그인 버튼만 보임).
- 패스키 등록·로그인 성공 시 비공개 메모 3개와 등록된 패스키 목록(이름+등록일)이 열린다.
- 비밀번호를 입력하는 칸이 어디에도 없다.

### 안 될 때는 무엇이 보이나요
- 브라우저·기기가 패스키를 지원하지 않으면 "이 브라우저·기기는 패스키(WebAuthn)를 지원하지 않습니다." 메시지가 뜬다.
- 등록·로그인 창을 취소하면 "등록을 취소했거나 실패했습니다" / "로그인을 취소했습니다" 메시지가 뜨고 화면은 잠긴 상태 그대로 유지된다.
- 화면 하단 "요청·응답 로그" 패널을 펼치면 방금 무슨 요청이 어떤 상태 코드로 응답됐는지 그대로 볼 수 있다.

## AI와 내 판단 3줄 (확정 — 최종본은 [AI3줄.md](AI3줄.md))

- **AI에게 맡긴 일**: WebAuthn(SimpleWebAuthn) 등록/로그인 API 구현, 세션·challenge 저장소 설계(Redis+로컬 파일 폴백), Vercel 배포·Redis 연동 진행, Playwright+CDP 가상 인증기로 등록·로그인·챌린지 재사용·기기 분실·교차 계정 시나리오를 자동으로 재현해 증거(스크린샷, 요청/응답 로그) 수집.
- **내가 직접 판단한 일**: 인증 서버를 어디에 둘지(Vercel 서버리스 + Redis 조합 결정), 비공개 영역에 넣을 더미 데이터의 구체적 내용과 계정 모델(아이디 기반, 이메일/실명 없음), 등록 성공 시 바로 로그인 처리할지 여부, "아직 못 막은 것"으로 username enumeration을 인정하기로 한 것, Vercel/GitHub 로그인과 Upstash 약관 동의는 직접 진행.
- **AI 말을 따르지 않은 일**: 없음 — 제안된 구현은 그대로 채택했지만, 채택 전 매번 로컬 자동화 테스트로 직접 재검증한 뒤에만 반영했고, 검증 스크립트가 놓친 케이스(등록 취소 시 아무것도 저장 안 되는지, 로그아웃한 쿠키 재사용 차단)는 직접 요구해서 테스트를 추가시켰다.

## 인증 구현 설명서 6항목 (확정 — 최종본은 [인증구현설명서.md](인증구현설명서.md))

1. **무엇으로 붙였나**: 라이브러리 사용 — `@simplewebauthn/server`(v13, 백엔드 검증) + `@simplewebauthn/browser`(v13, 프런트엔드 WebAuthn 호출). 직접 구현한 것은 challenge/세션 저장소, 계정·패스키 데이터 모델, 각 API 엔드포인트. 실제 갤럭시 기기로 등록해보니 패스키는 **삼성패스(Samsung Pass)**에 저장됨(T08-C26).
2. **왜 그걸 골랐나**: WebAuthn 명세를 처음부터 직접 구현하면 서명 파싱·CBOR 디코딩 등에서 실수하기 쉬워, 가장 널리 쓰이는 오픈소스 구현체(SimpleWebAuthn)로 검증 로직을 맡기고 저장·세션·API 설계는 직접 통제했다. 정적 사이트(GitHub Pages)에서 Vercel로 옮긴 이유는 서버리스 함수(api/*.js)로 challenge 발급·서명 검증을 실행할 곳이 필요했기 때문.
3. **어디를 어떻게 고쳤나**:
   - 등록: `api/register-options.js`(challenge 발급) → `api/register-verify.js`(검증+공개키 저장+세션 발급)
   - 로그인: `api/login-options.js`(challenge 발급) → `api/login-verify.js`(서명 검증+세션 발급)
   - 로그아웃: `api/logout.js`(서버 저장 세션 삭제 + 쿠키 제거)
   - 비공개 자료 조회: `api/private.js`(메모), `api/passkeys.js`(패스키 목록·삭제) — 둘 다 `api/_lib/require-session.js`를 통과해야 응답, 신원은 오직 세션 쿠키에서만 가져옴(`api/private.js`의 `session.username` 사용 부분 참고, 쿼리/바디의 username은 절대 읽지 않음)
   - 프런트엔드: `index.html`의 `#private-zone` 섹션 + `passkey.js`
4. **안 열리는 것을 확인한 기록**: `과제8/evidence/log.md`(자동 생성) + 스크린샷 4장에 아래 네 가지가 전부 포함됨
   - 로그인 없이 열기 → `/api/private` 401
   - 남의 패스키로 열기 → 양방향(alice→bob, bob→alice) 401 "이 계정에 등록된 패스키가 아닙니다"
   - 이미 쓴 질문 재사용 → 동일 로그인 요청 재전송 시 401 "이미 사용됨"
   - 패스키 삭제 뒤 로그인 → 삭제된 credential id로 시도 시 401, 남은 패스키로는 성공
5. **AI와 나**: 위 "AI와 내 판단 3줄"과 동일
6. **아직 못 막은 것**: `api/login-options.js`가 존재하지 않는 계정에는 404, 존재하는 계정에는 200을 돌려주기 때문에 아이디가 등록되어 있는지 여부를 외부에서 구분(사용자 이름 열거, username enumeration)할 수 있다. 또한 로그인 시도 횟수에 대한 rate limit이 없어 이 열거를 자동화로 반복하는 것도 막혀 있지 않다.
